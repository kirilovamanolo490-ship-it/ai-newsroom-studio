# AI 资讯来源库维护说明

本库从 https://daily.juya.uk/archive/ 的日报引用反查发布来源。首批范围为 2026-09-10 至 2026-10-10，含首尾 31 期。用途是扩展后续能持续发现新信息的入口，日报归档日期不等于原文首次发布时间。

本地页面：http://127.0.0.1:4311/source-library/ 。10 月 10 日日报页已经增加“来源库”入口。页面默认展示经过核验的目录和已识别账号，也能切换全部、X、网站/公众号、模型/代码、待核与受限来源。

## 数据链路

1. **发现日报**：读取橘鸦归档及 RSS，确认滚动一个月实际存在的各期；不存在或读取失败要记录缺口。
2. **提取引用**：只读每条新闻标题和正文“相关链接”，保留日报日期、新闻标题、新闻锚点和原始 URL。剔除该站导航、概览重复链接和截图/视频素材 URL。原文没有来源链接时不补造出处。
3. **识别发布者与目录**：X 的帖子落到作者账号；网站文章落到实际新闻/博客/研究/更新日志目录；GitHub 和 Hugging Face 落到发布者的仓库/模型列表。去掉路径最后一段只用于产生候选，必须实际核验。
4. **区分访问证据**：目录有多条内容或 RSS 列表证据才标目录已读取；单产品、单论文演示或表单页只作参考。能访问不等于官方身份；个人言论、社区转载和媒体报道不能升级为公司公告。
5. **公众号**：从真实文章页提取名称和 `__biz` 合并账号；在微信内从原文点击公众号名称进入历史。当前有部分文章缺少账号元数据，公开历史页也会要求微信客户端；这些均保留缺口，不伪造账号主页，不宣称已自动监控微信历史。
6. **持续发现**：已启用来源分别读取 RSS、网页目录、站点地图、X 新帖、GitHub 仓库变更和 Hugging Face 模型变更；再用新一期日报检查是否出现本库没有的新发布者。
7. **进入资讯候选**：保存新条目、旧条目修改和无日期新发现三类事件。编辑审核需重新核对发布者、原始时间、开放范围、发布时间与生效时间，确认后才进入日报、截图、视频及发布环节。本监测任务本身不外发。

## 文件位置与职责

- `sources/curated-library.json`：当前滚动月份的完整来源库。
- `sources/juya-directory-mappings.json`：跨月份保留的来源与原始链接对应关系。新核验结果替代当前月份旧映射，保留历史月份。
- `sources/official-watchlist.json`：真正启用的采集入口、方法和检查间隔。名称沿用早期文件，但内容包括官方、个人、媒体与社区，不表示所有条目都是官方。
- `research/juya-sources-日期/raw-links.json`：完整引用和缺失记录；`raw/` 保存实际读取的日报 HTML。
- `research/juya-sources-日期/directories-*.json`：初次目录核验结果；`*-overrides.json` 对明确的原始 URL 替换映射。
- `research/juya-sources-日期/directories-carried.json`：后续月份从主表带入的映射；存在该文件时，构建器以它为本轮目录输入。
- `research/juya-sources-日期/new-sources-pending.json`：当轮新来源队列。新网站不能仅凭同域名并到旧栏目，必须核验目录关系。
- `research/source-watch/state.json`：去重、成功时间、分页续传和每个入口的健康状态。
- `research/source-watch/runs/`：逐次读取证据与汇总；`latest.json` 是当前健康快照，每一行保留自己的实际读取时间。
- `research/source-watch/review-state.json`：由定时执行的助手记录已处理报告、事件、已通知故障，避免重复通知。
- `research/evidence/source-library/`：只供本地网页展示的 HTML、JSON、CSV 和说明，不放密钥、Cookie 或原始 API 凭据。

## 正常运行

在项目根目录执行。默认检查各入口是否到期，未到期不会重复读取；首次读取仅建基线，不把历史新闻推送为新增。

```sh
research/.venv/bin/python tools/source_watch.py
research/.venv/bin/python tools/build_source_library.py
```

2026-10-13本次调整起，现有ai-08-20任务改为“AI资讯：每2小时采集，08/20点汇总”，每天北京时间00、02、04、06、08、10、12、14、16、18、20、22点分别新建独立聊天执行。每批处理前2小时并入库；除08/20外的10个偶数时点制作《AI此刻》短视频与图文，08/20先完成最后一批再汇总六批出综合视频与图文。06–08与18–20不独立出短片，每天共12条视频。重要事件作为当期主题和独立特别报道图文。8点为触发时间，实际制作完成时间据回执记录。

新批次首次执行 `research/.venv/bin/python tools/source_watch.py --force`，覆盖所有已启用自动来源，绕过各入口原有1、2、6、12小时到期门槛；这些配置仍供手动默认命令使用。恢复同批次仅以 `--only` 补未完成来源，保留成功水位和分页游标。manual_watch_only保持人工网页核验，不能称每两小时自动抓取成功。状态通过 `research/news-batches/`、生产回执与来源回执交接，不依赖旧聊天。固定窗口、六批输入与缺口检查使用tools/news_batch.py，详细契约见research/report-redesign/早晚报制作规范.md。旧“ai”任务在应用中已不存在。本机及 Codex 需要可运行。只有有价值的新内容、特别报道完成、综合资讯完成、影响覆盖的新故障/恢复或需要用户操作时通知；无可靠新增且状态无变化时保持安静。

采集后须按运行编号顺序审阅 `runs/` 中所有尚未处理的 `report.json`，不能只审阅 `latest.json`；后者是会被下一次运行替换的健康快照。保存的逐次报告才是补查尚未整理事件的依据。

`review-state.json` 中的 `pending_editorial_batches` 是已保存但尚未完成内容分流的批次。推进报告审阅编号不能丢弃这些批次；处理完应记录每项是已核原文、待核事实、已覆盖消息或普通噪声，再移出队列。来源核验完成不等于成品日报、截图、视频或平台发布完成。平台发布按目标平台分别记录：仅向当前已绑定的平台提交，未绑定平台跳过，不阻塞其它平台；必须先通过现有本地视频验收。上传器明确返回 `submitted_unverified` 且 `exit_code=0`，或返回平台 `processing` / `public` 状态，即视为该平台提交流程完成，不再例行打开创作者后台核验、切换账号或重新登录。保留原始回执和准确状态，不把提交、处理中或公开状态改写成 `independently_verified_public`。失败、账号无效和结果含糊分别如实记录；只有这些失败状态才需要后续动作。已有成功回执时不得重复上传。

已通知的原文 URL 用于相同消息去重，不是永久屏蔽该地址。价格、权益、停用政策或协议正文的重要内容修订，即使仍在同一个 URL，也应重新核验修改版本；记录新旧差异、修改时间和生效时间后再判断是否通知。

新一期日报出现、近期日报修订或日期变化时：

```sh
research/.venv/bin/python tools/juya_sources.py
research/.venv/bin/python tools/refresh_juya_mappings.py --data-dir research/juya-sources-YYYY-MM-DD
```

`YYYY-MM-DD` 换为本次实际数据目录日期。默认包含首尾一个月；可显式传 `--start` 和 `--end`。近两期重新读取，更早的日报可复用已保存 HTML；全面回查旧期修改时使用 `--refresh`，不把旧缓存声称为本轮新读取。

检查新增队列，逐项实际定位目录。把结果写回当次 `directories-carried.json`（或独立覆盖文件），保留每个 `covered_urls` 对应原始 URL，再执行：

```sh
research/.venv/bin/python tools/build_source_library.py --data-dir research/juya-sources-YYYY-MM-DD
research/.venv/bin/python tools/connect_library_watch.py
research/.venv/bin/python tools/source_watch.py
research/.venv/bin/python tools/build_source_library.py --data-dir research/juya-sources-YYYY-MM-DD
```

构建器遇到未归属原始 URL 会拒绝生成完成清单。入口已登记与采集成功分别展示。`sources.csv` 是来源清单，`citations.csv` 是逐条日报引用对应表。

## 失败、日期与覆盖边界

- `source_watch.py` 退出码 2 是部分入口失败或覆盖未完成，必须读具体回执，不能据此整批重跑或清空水位。
- X 有限页未读完保留固定查询时间窗口和续传游标，不推进成功时间。X 初次基线是有界近期窗口，并不是该账号完整历史归档。
- X 小时时间窗使用 `since_time` / `until_time` 的 Unix 秒级过滤，并校验返回帖子的作者和时间范围。2026-10-10 已修复旧日期时间字符串导致同一天误返回空结果的问题；136 个既有账号均保留去重记录完成补查。补回帖子记录为回溯发现，不冒充刚刚发布。诊断、对照查询和修复前状态保存在 `research/source-watch/recovery-audit-2026-10-10/`。
- RSS 太短或 Hugging Face 返回数量上限无法覆盖上次成功时间时，明确记录覆盖缺口；需要补查归档/分页后才能认定连续覆盖。RSS 可配置发行方实际支持的 `feed_params`；Business Insider 已验证 `limit=100`，检查周期为 1 小时，其他来源的参数与周期保持各自配置。
- GitHub 发布者仓库目录按更新时间降序分页，直到覆盖上次成功水位。单轮默认最多 3 页；未完成时保留固定窗口和 `resume.next_page`，后续只继续未读页。中途请求失败保留此前已读页与游标，不推进成功时间。首次基线仍为有界首批，不声称已读整个组织历史。2026-10-11 已用实际分页补齐 Google 和 Microsoft 的单页覆盖缺口；测试与现场回执保存在 `research/source-watch/verification-2026-10-11-0315/`。
- GitHub 组织列表检查仓库新增与更新；重要单仓库可额外配置提交监测。Hugging Face 当前自动检查模型列表，Space、Collection 和讨论区不保证完整覆盖。
- 普通网页检查正文及链接变化，可能包含导航、榜单或旧页修订噪声，需要编辑审核。依赖浏览器渲染的页面可能被直接读取器标为失败；不能把空壳 HTTP 200 当成功。
- 目录已读与自动接通分别核验。`manual_watch_only` 表示实际通过网页工具确认过多篇目录及原文归属，但常规读取403/401；对应配置以 `manual-` 开头且 `enabled: false`，不宣称已自动监控。当前包括OpenAI Trust & Transparency及WSJ AI目录。
- 2026-10-11已核验FT Technology公开RSS `https://www.ft.com/technology?format=rss`，实际含25条当期标题/摘要/时间，按6小时周期读取；文章正文订阅限制仍保留。WSJ旧RSS `https://feeds.a.dj.com/rss/RSSWSJD.xml` 最新记录停在2025年1月，未启用为实时入口。
- Claude Help Center 额外读取官方 Sitemap 的英文文章清单，`lastmod` 只表示修改时间；查到新帮助文章后仍需打开正文核实发布时间和产品政策。
- 公众号历史、付费媒体或反爬页面没有接通的部分在页面中明确显示。其他渠道能补漏，但不能承诺全网绝对不漏或证明某条是全网最早。
- API 凭据只从 `.secrets/providers.env` 在脚本内部读取；不得打印或复制到公开文件。本流程不依赖 Firecrawl。
